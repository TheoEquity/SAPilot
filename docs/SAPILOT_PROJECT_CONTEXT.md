本文记录 SAPilot 的产品目标、领域约束与开发准则。**目标描述不代表当前版本已经实现。** 当前行为以源码、配置和运行验证为准；README 或本文件中的规划不能替代实现证据。

文档导航见 [文档入口](README.md)，文件放置和提交规则见 [项目目录约定](zh-CN/reference/project-layout.md)，当前组件与执行链路见[当前架构与消息处理流程](zh-CN/design/current/current-architecture-and-message-flow.md)。用户于 2026 年 10 月 29 日明确本轮采用 4核16GB 云机与千问 3.8 Flash API 的云部署方向，见[云部署讨论稿](zh-CN/design/discussions/cloud-api-deployment-draft.md)；此前完全离线和 8GB 显存的[离线架构讨论稿](zh-CN/design/discussions/offline-deployment-draft.md)已作废。继续按 50 名使用者和高峰 20 人提问规划，容量尚未压测；云部署方向已确认，不代表讨论稿中的所有建议均已定案或实现。

开发、调试和日常验证继续在本地进行；云服务器用于后续团队部署与使用。本地开发环境与团队部署环境分开，生成模型仍按已确认的 API 选型接入。

## 1. 项目定位

**项目目标：** SAPilot 运维领航员是基于 ApeRAG 二次开发的 SAP 运维 AI 助手，服务对象是 SAP 运维顾问。产品目标不是通用聊天，而是基于可靠证据完成故障问诊、知识检索、代码理解和制度查询。

**当前已实现：** 未逐项审计；不得由上述目标推断实现状态。

## 2. 本期业务范围

**项目目标：**

- FAQ 问答
- SAP 知识问答
- ABAP 代码阅读助手
- 运维规章制度检索

本期不建设跨会话长期 Agent Memory。会话历史可以持久化，但不同会话默认隔离。

**当前已实现：** 尚未核验四类场景的路由、隔离边界及持久化行为。

## 3. SAP 领域语义

准确识别并原样保留 FICO、MM、ABAP 等模块或技术术语；T-code、Message Error Number、错误文本；表名、字段名、程序名、事务码、参数、SID 等标识；以及中英文混合 SAP 问题。

不得擅自翻译、改写或补全无法从证据确认的专用标识。

**当前已实现：** 尚未通过代表性输入和输出核验标识保持能力。

## 4. 知识形态与摄取要求

**项目目标：**

- 左文右图 FAQ 文档：保持问题、原因、步骤、图片之间的原子关系。
- 上文下图 Message Error 文档：保持错误号、错误文本、说明和截图之间的对应关系。
- 运维规范文档：保留标题层级、适用范围、版本、生效时间和操作约束。
- ABAP 代码文档：保留代码结构、注释、对象名和上下文。
- 支持 PDF、Word、文本及经批准的源代码格式。

修改 Ingestion 时必须验证结构和元数据是否保留，不能只验证“文件上传成功”。

**当前已实现：** 文件格式、解析结果、关系保留及索引元数据尚未逐项核验。

## 5. 知识来源规则

来源优先级固定为：

`企业内部已审批知识 > 与目标系统版本匹配的 SAP 官方知识 > 模型固有知识`

发生冲突时必须展示冲突及适用范围，不允许由模型自行覆盖高优先级资料。模型固有知识只能辅助解释、生成检索词或提出澄清问题。

本轮采用云部署与模型 API。企业资料上云及发送给外部模型服务的范围需获批准；访问 SAP 官方资料仍应通过白名单代理或安全网关，并记录审计。完全离线不再是本轮部署要求。

**当前已实现：** 来源排序、冲突呈现、外部访问控制和审计能力尚未核验。

## 6. Agentic RAG 行为

**项目目标：** 请求流程体现为：

`意图识别 → Skill 路由 → 问题澄清/改写 → 知识与工具检索 → 证据核验 → 回答或拒答 → 会话上下文更新`

四类业务场景使用独立 Skill 边界，按需配置知识库、模型、Prompt 和工具。证据不足时必须澄清或拒答，不能退化为模型自由发挥的一问一答。

**当前已实现：** 流程各阶段、Skill 边界和证据不足行为尚未逐项核验。

## 7. 安全要求

**项目目标：**

- 遵守客户的网络隔离与数据访问要求；本轮部署方向为云服务器与模型 API。
- 企业文档、代码、日志、截图和凭据不得发送到未批准的外部服务。
- 外部访问必须可关闭、可配置、可审计。
- 高风险生产操作必须提示验证、备份、审批和人工确认。
- ABAP 场景本期以阅读、解释和风险分析为主，不自动执行生产变更。
- 密钥和模型配置不得通过可能造成跨用户覆盖的共享可变状态传递。

**当前已实现：** 部署隔离、外部访问控制、审计、高风险提示及配置隔离尚未完成安全审计。

## 8. 二次开发原则

- 优先复用 ApeRAG 已有的解析、索引、混合检索、Celery、LightRAG、MCP 和会话框架。
- 围绕 SAP 场景做最小增量扩展，未经明确需求不重写底层平台。
- 不用固定 Skill ID 表达业务能力，应使用可配置的语义角色。
- 代码是当前行为的事实来源；README、讨论稿和规划不能代替源码及运行验证。

## 9. 测试与验收

影响知识摄取、检索或回答的修改必须进行与风险相称的验证，覆盖以下三层：

- **Ingestion：** 解析状态、结构、FAQ/图片关系、元数据和索引结果。
- **Retrieval：** MRR、Recall`@1/3/5`、图片召回；明确不采用 MMR。
- **Answer & Golden Rules：** 事实覆盖、引用、拒答、冲突处理、标识准确性和高风险操作规则。

复用现有 SAP Basis 测试集，不得用单一 Ragas 分数掩盖摄取或检索失败。

**当前已实现：** 测试集覆盖及上述指标的现状尚未核验。修改时应先查找并复用仓库已有测试集和评估入口。

## 10. AI 开发工作准则

遵守以下八项工作原则：

1. 修改前检查现有实现、调用链、相关测试和官方接口文档。
2. 明确区分已实现、部分实现、规划目标和待确认规则；没有证据时标记未知。
3. 不得臆造 SAP 业务规则；资料无法确认时明确指出并询问。
4. 保持改动范围最小，优先复用已有能力，不做无关重构或顺手优化。
5. 每项修改都要附带与风险相称的验证；未执行的验证如实说明。
6. 不覆盖用户已有修改；写入前检查工作区状态并保护既有内容。
7. 不把建议、规划或他人意见当作用户决定，也不把建议、批准、执行、送达和完成混为一谈。
8. 结论回到原始材料核实；明确事实、推断和未知，并保留会影响后续决定的限制条件。
