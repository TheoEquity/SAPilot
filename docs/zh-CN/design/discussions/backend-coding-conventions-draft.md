## 2 公共能力的范围与复用建议

公共能力按调用范围和对外契约判断，不只看目录是否名为 `common` 或 `utils`。位于业务目录但被多处使用的方法，也可能属于公共能力；对外接口即使只有一个前端调用点，也有契约影响。

建议纳入公共变更判断的范围包括：

- 数据库连接、事务、缓存、对象存储等基础能力。
- 共享鉴权、异常处理、审计、配置加载及公共工具。
- 多处复用的模型调用、Agent 会话、检索、解析、索引和任务执行能力。
- API、WebSocket 契约、共享模型、数据库结构，以及全局默认配置。
- 会影响其他业务调用者的 Service 方法。

写业务代码前先检索现有实现及实际调用者，核对参数、权限、默认值、事务与其他副作用。能力适用时直接复用；不适用时说明差异，不强行调用，也不为规避公共变更审批而复制一份到业务模块。

## 3 公共变更审批建议

下表是拟议边界，详细范围尚待确认。所有操作仍须处于用户已授权的任务范围。

| 操作 | 建议处理 |
| --- | --- |
| 按原有契约调用公共能力 | 直接复用，不因调用本身增加审批 |
| 增加单个业务内部的私有逻辑，且不影响公共契约 | 在任务范围内实现 |
| 修改公共实现、签名、参数、默认值、返回值或异常行为 | 先提交具体方案，经用户确认后修改 |
| 新增公共能力，或将业务逻辑提取为公共能力 | 先说明复用对象、必要性与设计，经用户确认 |
| 修改共享契约、数据结构、全局配置或公共生命周期 | 按公共变更处理，先说明影响并确认 |
| 当前会话已经明确批准的具体公共变更 | 按批准范围执行，不重复确认；范围扩大时另行说明并确认 |

新增带默认值的参数、认为兼容的修复、公共文件格式化或重命名，也不自动豁免公共变更判断。发现 bug 或测试通过，不能代替所需确认。自动修复、生成代码和批量格式化前，应检查是否会改到未授权的公共部分。

### 修改前应提供的材料

先完成只读调查，形成可审阅的具体方案，再请求确认。建议说明：

1. 要改的文件、函数、字段或契约，以及当前行为。
2. 已查到的调用者和影响范围；未能确认的使用方明确标为未知。
3. 为什么现有能力不足、是否有仅在业务侧组合即可满足的方案。
4. 拟修改内容与前后行为差异，包括兼容性和资源权限影响。
5. 验证方式、必要的调用方适配，以及如何撤回本次改动而不覆盖既有工作。

等待确认期间不先修改相关公共代码；与该确认无依赖、且已获授权的工作可以继续。没有回复不等于批准，部分批准不能扩展为整套方案批准。

批准只覆盖明确范围，不代表实现完成或验证通过；实施后仍需报告实际改动与检查结果。

## 4 路由与 Service 等层次职责建议

本项目使用 FastAPI，用户所说的 Controller 主要对应 `views/` 中的路由函数，沿用现有命名即可。

| 层次 | 主要职责 | 编写边界 |
| --- | --- | --- |
| `views/` 接入层 | 接收与校验协议参数、取得用户身份、调用 Service、返回响应 | 不堆业务规则、模型提示词、检索流程或数据库操作 |
| `service/` 业务层 | 业务规则、资源权限、事务协调与流程组织 | 不承担具体 HTTP、WebSocket 的序列化与发送细节 |
| `agent/`、`flow/` 等执行模块 | 意图路由、节点执行、上下文等专门逻辑 | 不混入渠道特有逻辑；复用已有执行与会话能力 |
| `db/repositories/` 数据访问层 | 查询与持久化操作 | 复用已有会话与事务机制，保留用户及资源过滤条件 |
| 模型、存储、检索等适配模块 | 封装对应外部能力 | 由业务协调调用，避免每个业务另写客户端与配置流程 |

现有代码存在 Service 组织数据库事务回调的做法，后续应先保持事务语义，不以新规约为由立即重写存量实现。不要求每个函数都增加转发层，也不以文件行数作为强拆依据。

存量中的跨层调用按任务范围逐步核对，不由规约直接推导为必须全仓整改；调整公共路径仍遵循相应审批建议。

## 5 日常编码约定建议

- **最小范围**：只完成当前目标所需改动，不顺手重构、升级依赖或修正无关行为。
- **后端核验权限**：取得当前用户身份后，核对 Bot、会话、知识库、文件、模型和工具等资源范围；不以用户提交的 ID 或前端已校验作为授权依据。
- **复用异常体系**：优先使用现有业务异常和处理入口，不随意增加响应包装或改变状态码。WebSocket 按自己的消息契约处理，不能机械套用 HTTP 响应。
- **状态归属清楚**：请求数据、用户凭据和会话上下文不能通过共享可变配置造成跨用户覆盖；不擅自扩大缓存或单例的状态范围。
- **异步与后台任务**：避免在异步请求中引入阻塞操作；耗时解析和索引沿用后台任务，明确失败、取消和重试对状态的影响，不未经证据增加重试或锁机制。
- **事务范围清楚**：优先复用现有数据访问入口；关联写操作保持必要原子性，避免顺手改变提交、回滚和任务触发时机。
- **接口变更同步契约**：按 OpenAPI 与代码生成流程调整类型，在隔离输出中比较后再有范围地更新；不只修改生成文件，也不直接覆盖已知与定义不同步的产物。
- **日志与审计**：复用现有定位和审计能力，记录必要的请求、会话或任务标识；不直接输出密钥、凭据和完整私有文档，审查错误详情中是否含敏感信息。
- **命名与类型**：沿用模块现有命名与类型约定；公共参数、返回和关键业务结构尽量明确，避免依靠未经校验的任意字典隐含契约。

以上建议不能用于自动改写既有业务规则。配置优先级、提示词、路由、检索与拒答等行为的变更，应与纯结构整理分开说明和验证。

## 6 验证与交付建议

优先使用仓库已有 Ruff、mypy、pytest 和相关本地运行入口；具体命令按当前环境核对。全仓检查有历史问题时，区分基线与本次引入的问题，不为了检查通过扩大修复范围。

| 改动类型 | 对应验证重点 |
| --- | --- |
| 业务私有逻辑 | 受影响输入输出、异常与实际业务路径 |
| 公共能力 | 受影响调用者、兼容性、权限与错误路径 |
| 接口与数据模型 | 定义、生成结果、调用方和实际响应一致性 |
| 会话与流式处理 | 用户与会话隔离、事件、取消、错误、保存和必要恢复行为 |
| 数据写入与任务 | 事务、状态更新及相关失败或重复执行行为 |
| 摄取、检索或回答 | 按[项目背景](../../../SAPILOT_PROJECT_CONTEXT.md)验证结构保留、Recall 与 MRR、引用和回答规则 |

测试应覆盖真实行为与改动风险，不为文件搬迁或简单转发机械增加测试。公共纯逻辑和关键状态转换有行为修改时，应有能证明差异的回归验证。格式检查通过不等于业务验证通过。

交付时说明改了什么、依据是什么、实际验证了什么、哪些未验证，以及剩余风险与下一步负责人。开发、调试和日常验证继续在本地进行。
