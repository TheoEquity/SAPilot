# SAPilot 后端架构讨论稿

记录日期：2026 年 10 月 29 日。状态：讨论记录。本轮记录后端分层、Agent 职责拆分、配置契约及实施顺序建议，尚未执行重构或完成运行验收。

建议沿用现有 FastAPI、Celery、模型调用与检索体系，先明确模块边界，以 Agent 主服务为整理重点。API 与后台任务继续分进程运行，暂不因架构整理增加微服务或更换框架。

按 [AGENTS.md](../../../../AGENTS.md) 的讨论稿规则，常规实现与文档读取不以本稿为真源；用户明确要求基于本稿实施时，在指定范围内将其作为需求输入。当前行为以源码、实际配置和运行验证为准。

## 1 背景与范围

- 开发、调试和日常验证继续在本地进行，云服务器用于后续团队部署和使用；这是用户此前已确认的安排。
- 云部署与模型 API 方向见[云部署讨论稿](cloud-api-deployment-draft.md)，当前组件与消息链路见[当前架构与消息处理流程](../current/current-architecture-and-message-flow.md)。
- 本稿的后端拆分、试点与验收安排均为建议，不代表用户已确认全部设计细节，也不代表对应能力已实现。
- 第一阶段建议控制为拆清 Agent 主服务，保持现有接口、配置与业务行为。更换框架、拆微服务、修改检索策略不并入该阶段。
- [前端架构讨论稿](frontend-architecture-draft.md)中的界面与业务编辑整理需要与后端配置契约配合，但前后端重构不必同时执行。

## 3 建议的职责分层

| 层次 | 职责 | 对应现有基础 |
| --- | --- | --- |
| 接入层 | 接收请求、鉴权、参数解析和协议输出，处理渠道差异 | `views/`、WebSocket、钉钉入口 |
| 业务协调层 | 组织一次问答，协调路由、执行、返回、保存与错误处理 | `service/` |
| Agent 执行层 | 意图选择、Skill 节点执行、上下文准备 | `agent/` 与现有 Skill 执行代码 |
| 能力层 | 模型调用、检索、解析、索引及工具执行 | `llm/`、`flow/`、`mcp/`、`docparser/`、`index/` |
| 数据访问层 | 查询、事务、历史和文件存储 | `db/`、Redis 历史、`objectstore/` |

以上是职责划分，不要求每层增加框架或抽象接口。接入层适配协议，业务协调层提供明确的处理入口；模型、检索与存储能力按现有实现复用。

Web 与钉钉应尽量复用业务操作，渠道层负责输入输出差异。钉钉目前调用私有历史保存方法的边界，可在相关模块拆分时整理为明确的公共业务操作，不另建一套问答主流程。

## 4 Agent 主服务的拆分建议

| 模块 | 负责内容 |
| --- | --- |
| 消息协调服务 | 组织一次问答的步骤，协调完成、失败、取消及历史保存 |
| 意图路由 | 指定 Skill、规则匹配、模型分类和兜底选择 |
| Skill 执行器 | 动作、条件、起止节点及工具调用 |
| 上下文准备 | 模型配置、Prompt、知识库、历史与附件上下文 |
| FAQ 与附件处理 | 图片预检索、附件读取、FAQ 后续动作等具体业务分支 |

已有会话管理、历史管理、消息队列和事件格式化继续使用。先提取职责，保持既有路由顺序、提示词、模型参数、知识库回退与检索策略，避免把行为变更混进代码搬迁。

传统 Bot 的 Flow 与 Agent Skill 的执行路径继续区分。本轮不以统一名称或目录为由合并两套执行语义，也不在拆分时将现有固定 Skill ID 分支自动改写为新规则。

## 5 前后端配置契约

前端负责编辑、即时提示和错误展示；后端负责最终配置有效性、资源访问权限及执行条件。实施时先核对现有校验覆盖，再明确缺口，不能由前端已校验推断后端已保证。

需要核对的边界包括：

- 候选 Skill、兜底 Skill 和节点引用是否有效。
- 知识库、模型等资源是否属于当前用户可使用的范围。
- 配置字段是否仅被保存，还是实际参与执行。
- 保存与重新读取是否保留需要保留的字段，运行时配置优先级是否符合既有行为。

本次查看的意图分类路径未使用 `confidence_threshold`。类似字段与执行能力的差异应单独记录，不能在架构整理中悄悄增加新语义；补充校验或调整行为应明确范围并分别验证。

[后端模型文件](../../../../aperag/schema/view_models.py)标明由 `datamodel-codegen` 生成；[Makefile](../../../../Makefile)与[前端脚本](../../../../web/package.json)包含接口代码生成流程。修改接口字段时沿用 OpenAPI 定义与生成流程，避免前后端分别手改生成类型。内部模块拆分不要求修改对外接口。

## 6 问答与文档摄取分开

用户问答链路：

`接入 → 加载配置 → 意图路由 → Skill 执行 → 检索或模型调用 → 返回与保存`

文档摄取链路：

`上传与确认 → 后台调度 → 解析 → 建立索引 → 更新状态`

沿用现有 Celery、reconciler 与索引实现。耗时文档处理留在后台任务，聊天链路通过现有文档状态和上下文入口协作；不在架构整理中把完整摄取流程搬入聊天请求。

## 7 状态归属与未知项

| 状态 | 当前依据与后续核对 |
| --- | --- |
| 持久会话历史 | 已有 Redis 支持的历史管理；保存时机、失败与恢复行为需运行验证 |
| Skill 上下文缓冲 | 当前位于 Agent 服务实例内；重连、重启、多进程及不同渠道的表现待验证 |
| 模型与 MCP 会话 | 已有会话管理器；配置、凭据、历史及工具范围的用户隔离与并发行为待验证 |
| 文档与任务状态 | 已有数据模型和调度逻辑；失败、重试与重复执行需结合实际任务验证 |

使用 Redis 不能证明全部会话状态都已持久化或能够恢复。模块拆分应保留用户、Bot、会话与消息身份的传递，并核对资源范围，不能让共享可变配置造成跨用户覆盖。

上述待验证项不是已发现漏洞或已证实故障。是否需要调整存储、锁或生命周期，应在获取运行证据后决定，不提前增加机制。

## 8 建议的实施顺序

1. **建立行为基线**：记录指定 Skill、规则命中、模型分类、兜底、错误及响应事件；核对当前配置、入口和已有测试。
2. **提取意图路由**：保持原有顺序、参数、提示词和结果；核对路由结果、异常与模型调用次数。
3. **拆分上下文准备与 Skill 执行**：保留模型、知识库和 Prompt 优先级，以及节点与工具执行语义。
4. **整理渠道与业务分支**：明确 Web、钉钉的公共业务入口，分离附件和 FAQ 等处理，保持协议和既有响应格式。
5. **按证据处理后续问题**：配置校验缺口、状态恢复或执行语义调整单独列项，不在拆分中默认修正。

每步范围以实际调用关系为准，保留既有未提交工作。开发与验证在本地完成，再考虑团队云部署。

## 9 第一阶段验收建议

- 意图路由提取前后，指定 Skill、规则命中、模型分类、非法输出与兜底行为一致；模型调用条件和次数符合基线。
- 对外接口、配置格式、流式事件顺序与结束语义符合原有契约；传统 Bot 路径未受误改。
- 与改动相关的用户、会话、知识库及工具访问范围得到验证。
- 覆盖成功、错误、取消、历史保存及必要的重连场景，不把接口能通等同于业务通过。
- 优先复用[现有测试](../../../../tests/)，补充与改动风险相称的回归验证；现有测试文件存在不代表已覆盖完整 Agent 主链路或已通过。
- 涉及摄取、检索或回答效果时，按[项目背景](../../../SAPILOT_PROJECT_CONTEXT.md)复用 SAP 测试集，分别验证结构保留、Recall 与 MRR、引用及回答规则。
- 执行适用的静态检查、相关测试和本地集成验证后，才能标记对应阶段完成；未执行或不具备条件的检查明确保留。
