## 2 组件复用与职责建议

- 编写前先检索已有组件及使用处，核对功能、Props、事件、样式变体和交互状态，能力适用时优先复用。
- 新增业务界面优先组合现有组件，保留当前 UI。暂不引入网上组件，也不为相似控件另建一套基础实现。
- 基础组件只处理通用显示与交互，不感知 Bot、Skill、知识库，不请求业务接口或维护业务权限。
- 通用组合承担页面布局、表单分区等跨业务需求；业务组件负责对应功能，状态、请求和配置转换按职责组织。
- 单个业务可以有自己的组合组件和私有逻辑；出现实际共享需求后再提取公共能力，不按固定行数或使用次数强制抽象。
- 新增与拆分文件默认跟随现有业务模块就近放置；跨页面共享及 `features/` 的采用条件以架构稿第 3 节为准。
- 不复制公共组件源码来绕过修改审批，不通过全局选择器或运行时替换悄悄改变公共组件行为。
- 保留现有 Props 与事件语义，明确受控值、默认值和回调；基础组件不反向导入业务模块，跨页面共享实现不依赖 `app/` 路由内部文件。

## 3 公共能力范围与修改前审批建议

公共范围按实际调用者、共享样式和对外使用方式判断，不只看目录。建议包括：基础组件、通用页面和表单组合、共享 Hook 与 Provider、`cn()` 等工具、主题和全局 CSS、公共布局、API 客户端、共享类型及会影响多处的配置。

授权判断、修改与新增公共能力、已有批准的沿用，以及范围扩大的处理，统一按[正式公共变更边界](../../../../specs/development-workflow.md#公共变更与已有授权)执行，不在本稿另设一套审批表。前端按现有 Props、变体、事件复用组件，或使用已有 `className` 等扩展点调整当前业务布局且不影响其他调用方，属于任务范围内的正常使用；不能通过扩展点绕过公共行为变更判断。

认为兼容的可选 Props、新变体、bug 修复、重命名和公共文件格式化，也不自动豁免公共变更判断。升级依赖、运行组件安装器、自动修复或生成代码前，应检查是否会修改未授权的公共内容。

### 审批前的材料

先完成只读调查，提供可审阅的方案：要改的文件与组件、当前及拟议行为、为什么现有组合方式不足、已查到的调用方、视觉和交互影响、兼容方式、验证及撤回安排。未确认的调用范围明确标为未知。

待用户确认后再修改相关公共代码；无依赖且已获授权的业务工作可以继续。未回复不代表批准，部分批准不扩展为整套方案批准。审批通过与实现、验证通过是不同状态。

## 4 样式与 UI 约定建议

- 沿用现有 Tailwind、主题变量、`cn()` 和 `cva`。颜色优先表达为 `primary`、`muted`、`destructive` 等既有语义，不在页面中反复定义另一套品牌色、圆角或间距体系。
- 组件局部差异优先使用已有 Props、变体和布局组合。重复且含义一致的样式可以收敛为组件或变体；涉及公共修改时先按对应边界确认。
- 全局 CSS 保留主题与基础规则，不将某个业务页面的修补样式放入全局。不随意覆盖裸标签、第三方类名或公共内部结构，也不反复使用 `!important` 掩盖冲突。
- 复杂局部样式按需要使用 CSS Modules。图表、画布坐标等运行时数值可以使用必要的动态样式，不机械禁止所有行内样式或任意值。
- 新样式覆盖明暗主题、常用窗口宽度、文本换行和溢出，以及 loading、disabled、错误等相关状态；不以重构为由重新设计页面。
- 保留语义化控件、Label、键盘操作、焦点与必要的可访问名称，避免将已有可操作控件替换成只有点击事件的普通容器。
- 不批量引入未使用示例；评估 CSS、JS 的实际加载变化，不能由类名少、文件少或组件拆分完成推断性能改善。

## 5 状态、表单与副作用建议

- 每份可编辑数据有明确持有者。服务器快照、未保存表单、画布草稿与组件临时交互状态分开，不维护互相覆盖的多份可写副本。
- 优先沿用已有 React Hook Form、Zod 和适当范围的 Context；本轮不增加状态管理库或把业务临时状态全部提升到全局。
- 派生值尽量计算，不通过多个 Effect 同步同一含义的数据。Effect 用于确有需要的外部同步，不用来堆叠业务流程。
- 请求、订阅、计时器、WebSocket、预览 URL 等副作用明确生命周期和清理；关注切换 Bot、Skill 或会话后的旧响应覆盖问题，按实际风险处理。
- 保存逻辑明确输入、校验、pending、成功和失败状态；普通保存、快捷保存等入口保留各自语义，不能在抽取公共逻辑时暗中统一行为。
- 尊重现有 Server 与 Client Component 边界，交互部分按需使用客户端组件，不为便于引用将整个页面树改成客户端。

## 6 接口、类型与文案建议

- 业务请求优先使用已有浏览器或服务器 API 入口，保留鉴权、语言、路径和错误处理语义；业务私有请求逻辑不进入基础 UI 组件。
- 现有直接 `fetch` 调用先纳入盘点，再按范围处理，不因规约立即全仓替换请求方式。
- 按接口契约组织 Props 与业务类型，不以任意字典或类型断言长期掩盖字段差异；不单独手改生成文件或直接重生成覆盖已知不同步产物。
- 聊天沿用当前 WebSocket 协议，分别核对请求、实时事件和历史消息，不能为组件改造顺带改变后端协议。
- 沿用现有 next-intl 文案组织，用户可见的新文案进入对应语言资源。SAP 标识等按项目背景保留原文，不随意翻译或改写。
- 前端显隐和禁用仅是交互提示，不能代替后端权限核验；不将服务端密钥或私有配置放入浏览器代码、可公开环境变量或日志。

## 7 验证与交付建议

实施前记录受影响页面、调用方、关键状态及必要截图。验证范围与风险对应，不为简单样式修改机械新增测试框架或测试代码。

| 改动类型 | 验证重点 |
| --- | --- |
| 业务私有界面 | 输入、操作、成功与失败路径，明暗主题及相关窗口尺寸 |
| 公共组件、样式或布局 | 受影响调用方、Props 默认行为、视觉和键盘交互；不能只验证一个展示例子 |
| 表单与配置转换 | 初始值、校验、保存载荷、失败状态、重新加载及其他字段保留 |
| 共享状态或请求 | 页面与对象切换、刷新、请求失败及相关资源清理 |
| 聊天与附件 | 上传、状态、输入与发送、流式事件、停止、引用和历史等受影响行为 |
| 接口与生成类型 | 定义、生成差异、类型检查及实际调用的一致性 |

按当前依赖和环境核对适用的 TypeScript、ESLint、Prettier、构建及本地交互检查。现有脚本存在不等于当前一定能执行成功；Prettier 脚本会写入文件，构建、开发和 API 脚本也有安装、环境写入或清理等行为，执行前检查范围，不直接全仓自动修复或覆盖未提交工作。

检查通过才能报告对应结论；类型或构建通过不代替视觉与交互验证。交付说明实际改动、批准范围、检查结果，以及未验证项和下一步。开发、调试和日常验证继续在本地进行。
