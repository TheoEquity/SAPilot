## 2 表与字段设计建议

| 方面 | 建议约定 |
| --- | --- |
| 表的职责 | 说明保存的业务对象、数据归属与生命周期，先判断是否复用现有表，避免同一事实多处维护 |
| 命名 | 新增表与字段使用清晰的 `snake_case`，同一业务概念使用一致名称；关联模块沿用既有约定，不为统一单复数或前缀批量改名 |
| 主键 | 沿用适用模块的 ID 策略，说明生成方；不强制所有表改成同一种主键，也不擅自改变已有标识 |
| 关联字段 | 类型、长度和语义与引用对象匹配，说明物理外键或应用维护关系的选择及删除行为 |
| 类型与长度 | 按业务范围选择；计数用适当整数，需要精确计算的数值用定点类型；SAP 编号等标识保留字符串语义和前导零 |
| 空值 | 区分未知、不适用、空字符串与零；可空性需要业务理由，不一律允许或禁止 NULL |
| 默认值 | 明确业务含义、由应用还是数据库提供，以及是否适用于旧记录；不能用随意的空值或默认值掩盖缺失数据 |
| 时间 | 明确 UTC 与时区语义，说明创建、更新、删除时间的维护方；不只凭字段名推断自动更新 |
| 数据归属 | 明确用户、知识库、会话或 workspace 范围及查询条件，不在无需求时新增一套租户体系 |
| 状态与生命周期 | 定义状态值、合法转换、软删、恢复与清理；明确 `status` 和删除时间之间的关系 |
| 约束 | 根据业务定义非空、唯一、检查约束和关系完整性，明确唯一范围；不能仅靠先查后写保证并发唯一性 |
| 索引 | 根据实际过滤、关联和排序设计，说明支持的查询；避免每列建索引或重复已有索引 |
| JSON 与独立字段 | 经常查询、关联或约束的核心信息优先独立字段；灵活配置按查询与演进需求考虑 JSON 或 JSONB，不批量改造现有存储 |
| 版本字段 | 写清版本的业务含义、更新规则与使用者；存在 `version` 不等于已实现并发更新保护 |
| 敏感数据 | 标明敏感性、读写范围和必要的存储保护；不把密钥、私有文档等直接写入说明样例或日志 |

## 3 软删除与唯一性

PostgreSQL 默认不把唯一约束中的两个 NULL 视为相等。因此，把 `gmt_deleted` 放入普通联合唯一约束，通常不能保证删除时间为 NULL 的有效记录唯一。针对有效记录的唯一性，可以按业务范围考虑部分唯一索引，见 [PostgreSQL 约束说明](https://www.postgresql.org/docs/current/ddl-constraints.html)。

项目 Document 模型已存在 `WHERE gmt_deleted IS NULL` 的部分唯一索引，对应[迁移记录](../../../../aperag/migration/versions/20251119200541-332faa764121.py)。其他表还存在将删除时间纳入普通联合唯一约束的写法，后续应逐项核对业务唯一范围、其他可空字段、实际约束和现有数据，不能直接套用或批量修正。

每张使用软删除的表都应说明：

- 什么条件表示有效记录，普通查询怎样排除已删数据。
- 唯一性是全历史唯一还是仅有效记录唯一，范围是否包含所属用户或其他业务对象。
- 删除后是否允许复用名称，恢复时遇到冲突如何处理。
- 关联记录如何保留、删除或恢复，是否允许物理清理。

这些是待明确的设计项，不代表本轮已发现并修复运行故障。

## 4 默认值与时间维护

SQLAlchemy 的应用侧 `default` 与数据库 `server_default` 不是同一机制；设计时需说明不同写入路径是否都能取得预期默认值，见 [SQLAlchemy 默认值说明](https://docs.sqlalchemy.org/en/20/core/defaults.html)。

项目 Bot 布尔字段在模型中有应用默认值，[迁移](../../../../aperag/migration/versions/20260510100000-b2c3d4e5f6a7.py)也声明过数据库默认值。实际数据库是否保持一致需要单独核对，不能仅凭模型判断。

`gmt_updated` 等字段需明确由应用赋值、ORM 更新机制还是数据库维护，并验证相关更新路径；设置插入默认值不代表更新时会自动变化。修改全局时间维护方式属于公共行为变更，不在规约记录中直接实施。

## 5 设计说明与字段表模板

建议结构变更前先提供一份简短设计说明，至少包含表的用途、归属、生命周期、关联、唯一范围、主要查询与索引，以及下列字段表：

| 字段名 | 业务含义与单位 | 类型与长度 | 可空性 | 默认值及维护方 | 约束与关联 | 敏感性 |
| --- | --- | --- | --- | --- | --- | --- |
| 待设计 | 明确含义、取值或单位 | 按实际范围确定 | 说明 NULL 含义 | 应用或数据库，含更新规则 | 主键、唯一、检查或关联 | 明确读写范围 |

已有表变更还应补充修改前后差异、旧数据处理、受影响的 Service、API、后台任务及其他使用方。数据库字段与接口字段不要求机械一一对应，但映射和转换必须明确，参见[接口契约讨论稿](api-contract-and-integration-draft.md)。

## 6 结构变更审批建议

建议把新增或修改表、字段、索引、约束、默认值、关系和删除策略纳入公共变更范围。先提供设计与影响说明，经用户确认后再修改模型和迁移；已明确授权的具体范围不重复确认，范围扩大时另行说明。

审批材料包括：为什么修改、具体对象与调用方、旧数据兼容或回填方案、验证方式，以及失败后的回退或恢复安排。普通业务通过既有逻辑增删改记录，不全部算作结构变更；批量修复、删除或回填仍需明确操作范围。

设计确认、迁移代码修改、本地验证和向目标数据库执行是不同状态。代码修改获准不自动代表任意目标库执行也获准；应核对现有授权是否已明确涵盖目标环境和操作，不增加重复确认。

## 7 迁移与验证建议

- 模型变更配套 Alembic 迁移，不直接手改共享环境后补记录；不擅自改写已在其他环境使用的历史 revision。
- 自动生成只作为候选迁移，人工检查是否混入无关差异，尤其注意重命名可能被识别为删除再新增，见 [Alembic 自动生成说明](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)。
- 已有数据上的非空、类型和唯一约束变更，先检查空值、范围、重复与转换条件，设计必要回填；不以默认值自动代替业务判断。
- 评估目标表规模、锁和执行时长，根据实际需要安排实施，不预先引入额外迁移框架或复杂发布机制。
- 在本地隔离测试库验证空库建库、代表性旧版本升级，以及受影响的查询、写入、删除和恢复行为。
- 涉及默认值、时间、唯一性或关系约束时，验证相关应用与数据库写入路径，以及必要的并发和异常行为。
- 说明回退或恢复方式；存在 `downgrade()` 不代表删除、截断或覆盖的数据可恢复。必要的数据备份应验证可用性，不在用户数据上试验回退。
- 记录模型、迁移、实际表结构和相关接口的核对结果；未执行的升级、恢复或性能验证明确标为未知。

开发、调试和日常验证继续在本地进行。仅在实际检查通过后，才能标记对应迁移或设计要求已验证。
