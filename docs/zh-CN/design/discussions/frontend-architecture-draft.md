## 3 建议的四层职责

| 层次 | 职责 | 代码归属与边界 |
| --- | --- | --- |
| 路由与布局 | 页面入口、导航、权限入口、服务端初始加载 | 保留 `app/`，页面入口组合就近的业务实现 |
| 业务模块 | Skill 编辑、意图配置、聊天、附件等业务状态、规则与界面 | 默认在现有业务模块内就近放置；共享时按下文规则提取 |
| 通用界面组合 | 页面容器、标题、列表、表单分区等跨业务布局 | 复用已有 `components/`，有实际复用需求后再提取 |
| 基础组件 | Button、Input、Dialog、Select 等基础交互 | 沿用 `components/ui/`；不感知 Bot、Skill、知识库，不请求业务接口 |

依赖方向为：页面组合业务实现，业务实现使用通用组合与基础组件。基础组件不反向依赖业务模块。位于同一路由业务目录的页面、Hook 和私有函数可以相互引用；跨页面共享实现不依赖 `app/` 的路由内部文件，需要共享的类型和配置处理随实现一起提取。

文件放置默认按以下顺序判断：

- 已有业务的新增或拆分文件，跟随现有模块。例如 Skill 私有表单、Hook 和配置转换继续放在 `app/workspace/bots/[botId]/skills/`；聊天私有实现继续放在 `components/chat/`。
- 仅在当前页面使用的简单业务，直接在对应路由目录就近组织；复用同一业务能力时先查看该业务已有目录，不另建平行实现。
- 出现实际跨页面共享需求时，通用界面组合归入 `components/`，基础控件沿用 `components/ui/`；带业务规则、状态和请求的共享实现归入对应业务模块。`components/chat/` 是现有业务目录，不因位于 `components/` 就视为通用基础组件。
- 只有跨页面业务已经需要独立共享目录、且现有业务目录不适合作为归属时，才考虑 `features/<业务名>/`，并在具体任务中说明迁入文件、调用方与依赖方向。未触发该条件时沿用现有归属。

现有浏览器与服务器 API 入口继续使用；`web/src/api/` 中的生成代码不作为本轮手工重构对象。现有通用组件不为目录整齐而全部迁移。

## 4 业务模块内部的拆分

以 Skill 编辑器为例，按职责拆分：

| 部分 | 负责内容 |
| --- | --- |
| 编辑页面 | 组合基本信息、模型配置、Prompt、知识库、工具和画布区域 |
| 表单区域组件 | 显示字段、接收输入、显示校验信息 |
| 编辑逻辑 Hook | 初始化、加载选项、保存状态、协调校验与保存操作 |
| 配置转换函数 | 将表单和画布转换为后端配置，维护候选 Skill、默认路由等关联字段 |
| API 入口 | 复用现有请求客户端提交配置 |

配置转换尽量保持为不依赖 React 和网络的函数，方便核对输入输出。简单页面可以保留在一个文件中，不按固定行数强拆，也不要求每个模块都建立全部目录。

按上述默认规则，当前拆分的归属示例如下；它说明文件位置，不要求每个模块建立相同文件集：

```text
web/src/
├─ app/
│  └─ workspace/bots/[botId]/
│     ├─ bot-config-updater.ts  现有 Bot 配置保存入口
│     ├─ intent-router/         现有意图编辑模块
│     └─ skills/
│        ├─ skill-editor.tsx
│        ├─ skill-editor-fields.tsx
│        ├─ use-skill-editor.ts
│        └─ skill-config.ts
├─ components/
│  ├─ ui/                       现有基础组件
│  ├─ chat/                     现有聊天业务模块
│  │  ├─ chat-messages.tsx
│  │  ├─ chat-input.tsx
│  │  ├─ use-chat-messages.ts
│  │  └─ use-chat-attachments.ts
│  └─ …                         现有通用界面组合
├─ lib/api/                     现有浏览器与服务器请求入口
└─ api/                         生成的接口代码
```

## 5 编辑状态的归属

| 状态 | 建议归属 |
| --- | --- |
| 已保存的 Bot 配置 | 现有 Bot 配置 Provider，作为服务器配置快照 |
| 未保存的表单 | React Hook Form |
| 未保存的画布 | 当前业务编辑器，通过 `value/onChange` 与画布组件交互 |
| 节点选中、弹窗展开等临时交互 | 对应组件内部 |
| 候选列表、显示名称等派生数据 | 尽量从已有数据计算，避免重复存储 |

同一份编辑草稿应有明确的持有者，避免 Provider、表单和画布分别维护可写副本后互相覆盖。保存成功后的刷新、草稿重置与导航由业务编辑逻辑协调。现有 Context 和表单能力作为本轮基础，暂不增加状态管理库。

## 6 原试点顺序与后续安排

初稿建议先整理 Skill 编辑器，再处理意图编辑器，随后整理聊天连接和附件逻辑。后续已完成 Skill 与聊天、附件的局部拆分；下文保留原试点方法，后续任务结合实施记录确定剩余范围。

实施前，Skill 编辑器的普通保存和画布快捷保存重复构造 Skill、候选 Skill 和默认路由配置；现已集中到同一配置构造函数。原有重复是试点入口，不能仅据此认定保存存在 bug。

两个入口已共享配置构造，仍需分别保留现有触发方式、校验和交互语义。后续遇到真实行为差异时先说明差异，不在架构整理中自动统一产品行为。

原试点建议顺序：

1. 记录现状：页面截图、字段、保存入口、请求内容，以及保存后重新打开的配置。
2. 提取配置处理：集中转换与关联规则，继续使用现有 API。
3. 拆分界面区域：基本信息、运行模型、Prompt、知识库与工具、画布。
4. 验证试点：核对外观、操作、两种保存方式和重新加载结果。
5. 推广边界：整理意图编辑器，随后将聊天连接、消息处理与附件逻辑从展示组件中分离。

聊天模块继续适配现有 WebSocket 协议。模块拆分不构成改造后端消息协议的需求。

## 7 样式与新增组件约定建议

- 全局 CSS 保留主题、明暗模式和基础规则；组件使用已有主题变量与 Tailwind。
- 重复且语义一致的样式通过组件或 `cva` 变体统一；复杂特殊样式按需使用 CSS Modules。
- 同类基础控件复用同一实现；新增界面先定位所属业务模块，再组合已有组件。
- 通用组件只在出现实际复用需求时提取，避免提前建设庞大的组件平台。
- 不批量复制示例组件；源码中未引用的示例也可能进入 Tailwind 类名扫描范围。
- 样式优化按目标页面的 CSS、JS 加载量评估，不以手写 CSS 文件少或组件拆分完成代替性能验证。
