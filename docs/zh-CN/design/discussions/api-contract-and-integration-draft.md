## 1 已有基础与初查发现

项目已存在 OpenAPI，无需为本轮对接梳理另建一套接口描述体系：

```text
aperag/api/openapi.yaml 与引用的定义
├─ 后端 Pydantic 数据模型
└─ 前端 TypeScript 类型与请求 SDK
```

定义入口见 [openapi.yaml](../../../../aperag/api/openapi.yaml)，后端生成流程见 [Makefile](../../../../Makefile)，前端流程见 [package.json](../../../../web/package.json)和[生成器配置](../../../../web/openapitools.json)。流程存在不代表当前定义、生成文件与运行接口一致。

| 初查发现 | 源码依据 | 当前状态 |
| --- | --- | --- |
| 编排配置曾未完整进入定义 | 实施前 Bot YAML 缺少 `orchestration`，而后端模型与前端类型已有；当前 [Bot YAML](../../../../aperag/api/components/schemas/bot.yaml)已引用编排定义，[前端编排类型](../../../../web/src/app/workspace/bots/[botId]/orchestration-types.ts)已引用生成类型 | 本项已局部对齐并验证保存回读；范围和限制见实施记录，全量生成契约尚未对齐 |
| 聊天请求字段不同步 | 后端 `AgentMessage` 已有 `force_skill_id`、`action`，对应的 [Agent YAML](../../../../aperag/api/components/schemas/agent.yaml)中没有 | 静态核对，待对齐 |

## 2 页面与业务组件对照表

建议按以下关系梳理：

`页面入口 → 业务组件 → Provider 或 Hook → 接口调用 → 后端路由与服务 → 请求响应数据`

每条记录标明源码位置、用途和验证状态。基础 Button、Input 等组件记录复用与样式边界即可，不要求逐个绑定接口；一个业务组件可以对应多个接口。

初步样例仅用于说明表的粒度，不代表完整清单：

| 前端业务部分 | 调用方式 | 后端处理 |
| --- | --- | --- |
| Skill 与意图编辑器 | 经[配置更新函数](../../../../web/src/app/workspace/bots/[botId]/bot-config-updater.ts)提交 `PUT /api/v1/bots/{bot_id}` | Bot 服务保存配置 |
| 聊天输入框 | 上传附件、查询附件状态 | 聊天文档接口 |
| 聊天消息组件 | WebSocket 收发消息 | ChatService 分发至 Agent 或传统 Flow |
| 备份配置页面 | 直接 `fetch` 导出、导入及处理 Bot | 备份与 Bot 等接口 |

## 3 接口与契约对照表

建议每条接口记录以下内容：

| 信息 | 需要核对的内容 |
| --- | --- |
| 接口身份 | 方法、完整路径、用途、协议，以及正式入口或文档占位等性质 |
| 请求与响应 | 字段、必填性、默认值、响应结构、错误、分页或流式行为 |
| 访问范围 | 鉴权方式、用户与资源范围、前端调用入口 |
| 定义与实现 | OpenAPI 位置、生成 SDK 方法、后端路由与服务、前端调用文件 |
| 差异 | 缺字段、缺定义、类型不一致、未经过 SDK、声明与执行不一致等 |
| 验证状态 | 未核对、仅静态核对、已运行验证；附相应证据 |

定义存在但未发现调用、后端存在但缺少定义、仅用于文档生成等情况分别标记。未发现调用不能直接推出接口无用或可以删除。

静态定义、FastAPI 根据路由生成的 HTTP 描述、前端类型及实际请求结果需相互核对；任何一项单独存在，都不能证明整个契约一致。

## 4 聊天协议单独梳理

OpenAPI 主要描述 HTTP API，见 [OpenAPI 规范](https://spec.openapis.org/oas/v3.1.0.html)。项目中的聊天还需要单独记录 WebSocket 消息与连接行为，不以 HTTP 接口清单代替。

建议核对范围：

- 连接地址、鉴权、Bot 与会话身份，以及连接失败和断线行为。
- 请求中的问题、知识库、模型、语言、附件、指定 Skill 和 FAQ 动作。
- `start`、`message`、`thinking`、`tool_call_result`、`stop`、`error` 及 FAQ 选项等现有消息，逐项核对实际字段和前端消费方式。
- 事件顺序、内容追加、引用返回、停止与结束语义、历史保存。
- 请求消息、实时响应事件、持久化历史格式之间的区别。

初查入口包括[前端消息处理](../../../../web/src/components/chat/chat-messages.tsx)、[前端输入](../../../../web/src/components/chat/chat-input.tsx)、[后端响应类型](../../../../aperag/agent/response_types.py)和[Agent 主服务](../../../../aperag/service/agent_chat_service.py)。这些定义与消费位置尚未完成全面逐字段对照。

本轮不建议为记录协议立即增加新平台、改传输协议或统一全部消息格式；先把现有行为说明白。

## 5 建议的实施顺序与交付物

1. **盘点现状**：记录接口、页面、业务组件和调用关系，仅区分事实、差异与未知项。
2. **先覆盖核心链路**：Bot、Skill、意图配置；聊天与附件；知识库上传与检索；模型与 Prompt 配置，再扩展其余入口。
3. **补齐契约**：按源码和运行证据修正 OpenAPI 与聊天协议；功能或业务行为调整另列，不混入文档同步。
4. **验证生成流程**：隔离生成，比较现有与新产物，核对字段保留、前后端类型及实际调用；通过后再有范围地更新。
5. **进入模块拆分**：结合核对后的契约与测试，再推进[前端讨论稿](frontend-architecture-draft.md)和[后端讨论稿](backend-architecture-draft.md)中的试点建议。

建议交付物为接口与组件映射清单、契约差异清单、聊天协议说明。后续正式清单应逐条附源码或运行证据；本讨论稿不代替这些清单，也不将初查样例当成全部接口。

开发与验证在本地进行。梳理阶段不采购接口管理平台，不改变现有 UI，不引入网上组件，不执行无关重构。具体范围、首批文件和验证命令在明确启动实施后根据最新代码确定。
