## 图片输入为什么受阻

真实 PNG 已通过 multipart 上传，并按原字节取回验证哈希一致。修正临时 Bot 绑定后，MM-IMG-01 正式提问仍进入 basic_qa，无工具、引用或图片，要求用户转述截图内容；不能计为以图搜图成功。

另用真实附件调用原生 `search_faq_by_chat_image`：附件成功加载为 data URI，但返回空结果。相关 trace 与进程日志对应到 [图片检索服务](../aperag/service/image_search_service.py)的非多模态集合跳过分支。现集合嵌入模型 `text-embedding-v4` 未声明 multimodal，七份源文档也没有已接受的 VISION 索引。

PNG 解析另在 [ImageParser](../aperag/docparser/image_parser.py) 的 `PADDLEOCR_HOST` 检查处抛出 FallbackError，并出现重试。上传及存储成功不能代替解析成功。供应商模型自身是否支持原生视觉，本轮未进行供应商级请求验证，保持未知。

因此，正式实跑 1 题并用运行证据建立共同阻断，其余 11 题记录为 BLOCKED，未伪造各题答案或耗时。MM-IMG-06、MM-PART-06 两道澄清题也未逐题运行，未计 PASS。

本轮同时重新取回原文字题涉及的 41 个源图资产，全部 HTTP 200、哈希与摄取记录一致。**页图能存、能下载、能定位，与当前图片输入不能完成理解/检索可以同时成立。** 资产存在不证明模型看到了像素。

## 独立检索诊断

对原 26 题各执行一次原问题的固定 REST 检索：向量 topk=5、similarity=0.2，全文 topk=5，rerank=false，不保存搜索历史，26/26 返回 HTTP 200。它独立于 Agent 的改写、多轮查询，不用这组结果代替正式聊天的实际上下文。

目前提供的是**可核对的引文及图资产候选覆盖诊断**，不是已完成全部语义判断的正式 Recall/MRR：

| 24 道业务题，证据组宏平均 | 前 1 项 | 前 3 项 | 前 5 项 | 全部返回项 |
| --- | ---: | ---: | ---: | ---: |
| 引文/资产候选覆盖 | 25.83% | 43.82% | 49.72% | 89.51% |

按原 all_of 组核对规范化连续引文，保留标点和 ABAP 运算符，并限制真实来源、已验证替代来源及资产身份；多图必须满足所有必要资产。短串匹配仍不能证明完整语义、条件或图文区域，因此“保守诊断”不保证是人工语义 Recall 的数学下界。正式语义 Recall/MRR 还需按完整证据组逐题审定，不能据 89.51% 宣称八成召回已达标。

实际观察与源码依据：

- REST 每次实际返回 10–20 项。[全文节点](../aperag/flow/runners/fulltext_search.py)请求 `top_k * 3`，不能把整份响应当作 Top5。[MCP 工具](../aperag/mcp/server.py)另有 `items[:topk]`，REST 尾部候选不代表聊天已收到。
- [fallback 排序](../aperag/flow/runners/rerank.py)直接按全文和向量原分数降序。本批全文分数均高于向量，正确 ABAP 候选在 ABAP-01/02/03 中位于 11–15 名附近；ABAP-05 为 15/16/18；ABAP-04 全部 20 项都未召回 ABAP 文件，不能只归因为排得靠后。
- 这是固定查询的证据，不证明正式 Agent 每次都发生相同排序问题。正式提示要求分路检索，须分别查看各会话的工具调用。
- 10 个 `source=faq_table` 候选均保有可核对的真实 `metadata.name` 与 document ID，未据此误判为来源丢失。

上述统计器和原响应已由另一 Agent 直接复核，未采用只看摘要的审查方式；初版标点抹平造成的 ABAP 候选误匹配已在私有统计器中纠正，未改产品代码。
