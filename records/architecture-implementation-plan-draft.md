# SAPilot 架构整理推进计划讨论稿

记录日期：2026 年 10 月 29 日。状态：原推进顺序记录。初稿形成时仅提出计划；后续五批已实施，当前结果见下文链接。本稿保留原安排及理由，剩余建议不自动成为已批准需求。

后续进展：用户随后已要求逐批委派实施并逐批独立审核，五批已集成本地 main，并补验了 Bot / 编排真实保存回读；具体候选、审核、集成及未验证项见[实施记录](architecture-implementation-record.md)。第 1 至 4 节保留实施前的起点、差异与计划，不作为当前待办；第 5 节统一后续整理边界，第 6 节说明当前状态。

## 1 原计划起点与建议顺序

初稿形成时，现状说明、18 篇旧设计核对和接口—组件—配置字段盘点已完成静态整理，代码重构、配置往返保存和问答运行验收尚未完成。实施前依据见[契约盘点](../docs/zh-CN/reference/api-component-config-inventory.md)与[HTTP 对应表](../docs/zh-CN/reference/http-api-component-matrix.md)，后续实现入口见[当前说明](../docs/zh-CN/design/current/README.md)。

建议先以 **Bot / 编排配置保存契约**作为首批交付，再以 Skill 编辑器做前端试点，之后提取后端意图路由，最后推进聊天与附件整理。若本地基线发现阻塞目标操作的行为问题，先单列最小修复，再继续拆分。

这样安排的直接依据是：

- Bot 设置、意图编辑、Skill 普通保存和画布快捷保存共用 PUT Bot，后端直接替换 config；保存对象里未带回的字段需要先核对保留规则。依据：[更新器](../web/src/app/workspace/bots/[botId]/bot-config-updater.ts)、[BotService](../aperag/service/bot_service.py)。
- 实施前 OpenAPI 缺少 orchestration 等已有字段，生成类型还有手工扩展；当时直接全量生成可能覆盖这些扩展。该项已局部对齐，完整生成链的限制见实施记录；相关入口为 [Bot YAML](../aperag/api/components/schemas/bot.yaml)、[Python 模型](../aperag/schema/view_models.py)、[前端编排类型](../web/src/app/workspace/bots/[botId]/orchestration-types.ts)。
- 实施前 Skill 普通保存和快捷保存重复构造配置，Agent 主服务同时包含路由、上下文、节点执行和渠道协作，因此选择这两个模块试点。配置构造与意图路由现已分别提取；相关入口为 [Skill 编辑器](../web/src/app/workspace/bots/[botId]/skills/skill-editor.tsx)、[Agent 主服务](../aperag/service/agent_chat_service.py)。

以上是安排顺序的理由，不表示所有静态差异都是已经复现的故障。仅有定义、实际未执行的字段，也不自动成为必须补做的功能。

## 2 分批交付

每批形成一个可独立检查的变更和相称的验证结果，上一批必要检查通过后再进入依赖它的下一批。以下批次是工作范围，不是另建一套流程或按固定工期排期。

| 批次 | 目标与范围 | 交付物与通过条件 |
| --- | --- | --- |
| 1 Bot / 编排保存契约 | 核对配置基线，补齐首批已有字段的定义，隔离生成比较，明确并验证字段保留 | 普通设置、意图、Skill 普通/快捷保存后能回读应保留配置；相关定义与类型一致；不改变路由和模型执行语义 |
| 2 必要的行为修正 | 仅处理复现后阻塞本轮目标的差异，明确当前值、期望值和影响范围 | 每项单列正常与失败场景；修复后的实际参数或协议行为可验证，不将未实现规划一起补齐 |
| 3 前端 Skill 试点 | 提取配置构造与编辑状态，按职责拆表单区域，沿用现有 UI 和 API | 两种保存分别符合原有语义；其他 Skill、候选、兜底和 Bot 配置不被误改；页面与构建检查通过 |
| 4 后端意图路由试点 | 先提取指定 Skill、规则、模型分类和兜底；后续上下文/Skill 拆分另分小步 | 提取前后路由结果、模型调用条件/次数及失败结果符合已记录基线；保持渠道和资源身份传递 |
| 5 聊天与附件整理 | 在前述基线稳定后，分离连接、消息状态与附件业务，按需要整理 Web/钉钉协作入口 | 正常回答、引用、错误、取消/重连和历史回放按各自契约验证；无法验证的项保留为未知 |

开发、调试和验证仍在本地。团队云部署继续沿用此前确认的方向，部署准备放在相关本地链路验收之后；4核16GB 与模型 API 的选择不是吞吐、费用或效果验收结论。

## 3 首批建议直接做什么

### 目标

让当前已经支持的 Bot、意图和 Skill 配置在定义、类型、提交与回读之间形成可核对的契约，为后续提取配置处理和业务模块提供基础。

### 范围

1. 从相关源码和必要本地请求建立一组脱敏配置基线，包含 Bot agent/flow、意图候选与兜底、至少两个 Skill，以及已有高级字段。配置有默认值时，比较业务值，不要求 JSON 字节或键顺序相同。
2. 核对 Bot 设置、意图保存、Skill 普通保存与画布快捷保存各自提交什么、保留什么。只修改选定对象时，其他已认可且应保留的配置不得无意丢失。
3. 将当前 Python 已接受、前端已使用的 Bot/编排字段补入源定义，核对必填性、默认值与前端可选性。对应盘点 D01、D02；未生效字段如仍保留，明确其现状，不借定义同步增加执行语义。
4. 在隔离输出目录进行模型/SDK 生成和比较，检查编排与既有扩展是否保留。只采用本批对齐所需产物；其他生成差异记录后另行处理。
5. 若往返验证确认字段丢失，作为本批明确的保存行为修复单列说明，再验证两种保存与回读。没有复现的字段风险继续标待验证。

本批不要求先清完 127 个操作的全部载荷差异。聊天事件类型、Cookie 描述、工具列表和备份缺定义等按调用影响安排后续契约变更；主链实际需要时再纳入对应任务。

### 预计涉及的入口

| 部分 | 核对或修改边界 |
| --- | --- |
| 源定义 | `aperag/api/components/schemas/bot.yaml` 及确有需要的编排 schema 引用 |
| 生成类型 | `aperag/schema/view_models.py`、`web/src/api/`，通过隔离生成比较决定相关产物，不手工维护两套相互漂移的定义 |
| 前端配置提交 | `bot-config-updater.ts`、`bot-form.tsx`、意图与 Skill 编辑器中实际构造提交对象的部分 |
| 后端保存 | BotService 与序列化仅在确认需要修正保存行为时修改；不顺手拆 Agent 或改数据库模型 |
| 验证 | 相关模型解析、配置转换及本地保存—读取；复用合适的现有测试，按风险补必要回归 |

完整文件定位以[契约盘点](../docs/zh-CN/reference/api-component-config-inventory.md)为入口。公共接口、生成类型和共享配置提交函数都要在该批影响范围中明确；范围外变更按现有项目规则说明后再处理，不以讨论稿自动授权。

### 首批验收

- 对齐后的定义能生成预期字段与类型，已有编排字段、默认/保护标记及首批采用的扩展没有被意外覆盖。
- 保存指定 Skill 后，另一个 Skill、意图候选、兜底以及应保留的 Bot 配置可回读；意图保存和 Bot 设置保存也分别核对保留边界。
- Skill 普通保存与快捷保存各自通过相关场景；二者既有校验或触发差异被明确保留，需调整的行为单列说明。
- 已有高级字段在未编辑时的保留规则有实际结果；显式清空、默认回填与未提供字段不混为一种操作。
- 失败请求有可观察的失败结果，不把请求失败后的 UI 当作已保存；相关类型、构建与必要测试执行后再记通过。

这一步需要实际运行条件。现有 [test_bot.py](../tests/e2e_test/test_bot.py) 中仍有旧式 config 字符串与 collection_ids 请求样例，不能因文件存在就当作当前编排契约回归已覆盖或已通过；实施时核对相关 fixture，避免扩成全量测试重写。

## 4 已发现差异如何安排

| 事项 | 建议处置 |
| --- | --- |
| Bot/编排定义缺项、配置保存保留规则 | 首批处理并验证，是后续试点直接依赖 |
| 意图 provider、max_tokens 与实际参数不对应 | 按明确目标语义做独立行为修正；若阻塞本地问答基线，先于模块拆分处理 |
| confidence_threshold、启停、IO 与工具高级策略未完整执行 | 作为产品/执行语义待定项，不在纯拆分时自动补实现；必要时另提需求 |
| Agent 与传统 Flow 请求字段差异 | 先确认本轮使用的 Bot 类型；涉及传统路径时单独修正和验证，不强行统一全部协议 |
| WS error 收尾、取消与历史格式 | 先记录可观察行为，在聊天批次按明确范围修正或保留；断开连接不等同模型任务已取消 |
| 索引 Prompt、导出清理、标签授权等 | 继续留在[未实现规划](../docs/zh-CN/design/planned/README.md)，不并入本轮配置/编辑器试点 |

这里没有给全部差异统一贴“必须先修”的标签。优先级取决于是否阻塞选定交付；实际故障与新增语义分别记录。

## 5 前后端试点的完成边界

前端文件归属统一引用[前端架构讨论稿第 3 节](../docs/zh-CN/design/discussions/frontend-architecture-draft.md#3-建议的四层职责)：默认在现有业务模块内就近放置，实际跨页面共享时再提取；只有现有业务目录不适合承接共享实现时，才在具体任务中考虑 `features/<业务名>/`。Skill 配置构造、编辑逻辑与界面分区已完成局部拆分，意图编辑器等后续整理按具体任务确定。

后端沿用[后端架构讨论稿](../docs/zh-CN/design/discussions/backend-architecture-draft.md)的方向：意图路由已独立提取，已明确修正的行为作为新基线。上下文、Skill 执行、FAQ 和渠道入口按后续需要拆，保持传统 Flow 与 Agent 的语义边界。

每批检查实际改动、相关测试和本地业务场景。单个模块验证通过只说明该批结果，不能升级为整体 SAP 效果、并发或生产部署已通过。涉及摄取、检索和回答质量变更时，继续按[项目背景](../docs/SAPILOT_PROJECT_CONTEXT.md)的对应验收要求执行。

## 6 当前状态与下一步

已完成：当前实现文档、旧稿分类、静态接口与核心配置盘点，以及五批代码整理和局部验证；Bot / 编排另已补验真实 HTTP / 数据库保存回读。检查范围、历史限制与剩余项见实施记录，不能概括为完整运行验收通过。
