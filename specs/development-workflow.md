# 开发流程与公共变更边界

本文规定需求开发与维护的协作方式。产品与验收要求见[项目背景](../docs/SAPILOT_PROJECT_CONTEXT.md)，开发、调试和日常验证在本地完成。

## 需求与交付

1. 复述用户要解决的问题和预期行为。已有信息足够就继续；只有缺失信息会改变用户可见结果、范围或验收含义时才澄清，沿用已有明确决定。
2. 查看相关实现、调用方、配置与测试，说明改哪里、复用什么和必要影响。按[前端](frontend-architecture-and-conventions.md)、[后端](backend-architecture-and-conventions.md)、[数据库](database-design-conventions.md)、[接口](api-contract-conventions.md)规则确定归属，保持最小充分改动。
3. 开发前明确正常路径、必要异常和直接受影响的旧行为，不照实现倒推通过条件。需要公共变更时按下节核对已有授权。
4. 在授权范围内实施。按任务与执行环境约束使用子代理；需要并行时，每个文件或交付物有一个主要写入者，主代理整合实际内容与证据。目录调整、接口同步和行为变更分别说明，不顺手补功能。
5. 在整合后的待交付版本上检查需求、实际差异、文件归属和必要回归。发现具体缺陷后修复，再重跑失败项及直接受影响检查；原因不明时重新定位。没有新改动、失败或未解决问题时不反复扩大检查。
6. 交付说明改了什么、依据、实际检查、未验证项及下一步负责人。文档写完、代码写完、检查通过、集成、发送、部署和运行验收分别表述。

需求记录通常几行到一页，沿用该任务已有位置：

```text
目标：解决什么问题。
范围：本次工作及关键边界。
改法：改哪里、复用什么、是否涉及公共部分。
验收：哪些可观察结果代表通过。
验证结果：实际检查、结果和未验证项。
```

记录供跨任务继续使用，不为每个小需求额外生成多套 PRD、方案和报告，也不反复重做全项目架构调查。

## 公共变更与已有授权

本节统一维护前端、后端、数据库及接口的公共变更口径。公共范围按实际调用者和契约判断：共享组件、Hook、Provider、样式与主题、请求客户端、类型与配置、鉴权与审计、数据库与事务、存储、模型、检索、解析、任务，以及 API / WebSocket 契约等。

先核对用户指令或此前已确认方案是否覆盖具体公共对象、拟议改动及影响范围。已明确覆盖的直接执行，不重复确认；仅批准业务目标时，不自动推定所有公共改动都已获准。必要公共改动尚未被覆盖时，先完成只读调查、提供具体方案并取得确认。新增范围只确认新增部分，不按每个文件或每个开发阶段重复审批。

| 操作 | 处理方式 |
| --- | --- |
| 按现有契约调用公共能力，或在已有扩展点内组合业务功能 | 在任务范围内直接复用 |
| 增加业务私有逻辑且不改变公共契约 | 在任务范围内实施 |
| 修改或新增公共能力、提取共享实现、修改共享契约或结构 | 已有具体授权则沿用；未覆盖则先说明方案并确认 |
| 扩大已确认的对象、行为或影响范围 | 说明并确认新增部分 |

需要确认的方案说明对象与调用方、当前和拟议行为、现有能力为何不足、兼容与权限影响、验证及撤回方式。只记录会影响判断的未知项；前端补充视觉与交互影响，数据库补充旧数据处理和目标环境。

兼容参数、可选 Props、修复、重命名或格式化仍按实际公共影响判断；检查通过不能代替所需确认。自动修复、安装器和代码生成前先核对写入范围，不通过复制公共源码或全局覆盖绕过边界。等待必要确认时可继续无依赖且已获授权的工作；没有回复不等于批准。

## 验证与资料维护

- 验证与改动风险相称，优先复用现有测试和检查入口。不为简单搬迁机械新增测试框架，也不以纯风格偏好阻塞交付。
- 前端类型与构建、后端静态检查、接口回读等只支持对应范围的结论；按需要补实际业务与交互检查，明确历史基线问题和本次引入的问题。
- 涉及 SAP 摄取、检索或回答的变更，按项目背景分别验证结构与元数据、Recall 与 MRR、回答与引用等规则；单一自动评分不能替代分层验收。
- 保留未提交工作、分支与工作树；共享代码和文档放仓库，私有语料、凭据、模型权重及原始评测按[目录约定](project-layout.md)放置。移动文件核验哈希并同步引用。

## 规则文档维护

开发要求由 `AGENTS.md` 直接引用具体规范，README 仅作概览、解释与导航，不承载规则或必读步骤。规则变化更新对应规范及必要的直接引用；公共变更口径只维护在本文。讨论稿保留理由、备选与未采用建议，不维护第二套日常规则。

[工程架构概述](engineering-architecture.md)只定义高层模块、职责、依赖和边界；开发细则放在对应规约。接口操作、字段与请求响应由 FastAPI 路由和 Python 模型维护，不在架构文档中复制清单或固定接口数量；代码归属、文档导出与前端生成见[接口规约](api-contract-conventions.md)。

架构和规约保持稳定，只写职责、边界和开发规则；实施进展、完成状态、批次、来源及历史验证材料与正文分开，过程记录放在根目录 `records/`。只有任务涉及职责、依赖或约定变化时，才修改对应架构内容。

用户当前指令和已有明确决定优先，改动保持在任务必需范围内。
