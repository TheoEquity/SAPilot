# 全栈日志与问题排查规约

本文规定前端、后端和后台任务如何记录可关联的业务事件与异常，支持从一次页面操作追踪到请求、任务和失败依据。架构职责见[工程架构概述](engineering-architecture.md)，公共能力变更遵循[开发流程](development-workflow.md)。

## 统一工具与调用入口

| 范围 | 统一记录工具 | 业务代码的调用方式 |
| --- | --- | --- |
| 前端浏览器及 Next.js 服务端 | 基于运行环境原生 `console` 的项目轻量 `logger`，统一处理级别、结构化字段和脱敏 | 统一从 `web/src/lib/logger.ts` 导出 `logger`，通过 `@/lib/logger` 调用 `debug`、`info`、`warn`、`error`；浏览器与服务器共用调用接口，输出环境标识不同 |
| Python API、Service、解析与 Celery worker | Python 标准库 `logging` | 各模块用 `logging.getLogger(__name__)` 获取 logger，使用原生级别方法及 `extra` 传入业务字段；格式、级别、输出和上下文注入由公共配置负责 |
| 模型与调用链追踪 | 现有 OpenTelemetry、Langfuse | 复用现有埋点和上下文，关联应用日志，不作为前后端普通业务日志的替代入口 |

前端日志入口仅封装必要的级别控制、字段格式、脱敏和输出，不另建日志框架或为不同页面维护多套 logger。浏览器默认输出到开发者工具控制台，Next.js 服务端输出到服务进程的标准输出/错误；集中采集按下文另行接入，调用点不承担上传逻辑。

Python 各模块持有不同名称的 logger，仍属于同一套 `logging` 体系。API 与 worker 的启动配置遵循同一字段和输出规则，业务模块不自行调用 `basicConfig`、重复安装 handler 或另外配置文件输出；第三方及框架日志沿用兼容配置，避免重复打印。

日志配置集中在 `config/logging/`：`settings.json` 统一目录及轮转上限，`api.yaml` 配置 API 输出。默认日志目录为项目旁的 `../SAPilot-data/logs/`，可用 `SAPILOT_LOG_DIR` 覆盖；相对路径以项目根目录为基准。API、worker、前端服务分别写入 `api.log`、`worker.log`、`frontend.log`，默认每个文件 10 MB、保留 3 份轮转备份。浏览器诊断导出放在同目录的 `browser/` 下，验证归档放在 `verification/` 下；原始日志不放入源码、文档或过程报告目录。

新增和修改业务代码使用各端统一入口，不用散落的 `console.*`、`print` 或另一套日志库代替业务日志；前端公共 logger 内部的原生输出、框架自身输出及测试专用输出不在此限制内。已有零散日志在相关功能维护时按需收敛，不因采用本规约启动全仓替换。更换输出去向不要求逐个修改业务日志调用点。

工具依据：[Python logging](https://docs.python.org/3.11/library/logging.html)、[Console 标准](https://console.spec.whatwg.org/)。依赖与版本仍由项目清单维护，本约定不要求新增第三方日志依赖。

## 职责与代码边界

| 位置 | 日志职责 |
| --- | --- |
| 浏览器业务代码 | 上传、保存、发送消息等关键动作的结果，页面异常及 WebSocket 异常；携带相关对象和请求标识 |
| 前端请求入口 | 统一记录请求结果、耗时、状态码和关联标识；复用现有浏览器和服务器请求入口，不修改自动生成的客户端文件来打点 |
| Next.js 服务端 | 记录服务端请求、渲染或转发异常，传递关联上下文，与浏览器日志区分 |
| 后端 API 与 Service | 接口结果、关键业务分支、外部依赖失败及异常依据；协议入口和业务协调层分别承担自己的上下文 |
| Celery worker | 任务执行、阶段结果、重试及最终状态；记录解析、转换、OCR、分块和索引等实际经过的阶段 |
| 模型、检索与工具 | 调用结果、耗时、必要数量和模型/工具标识；复用 OpenTelemetry 与 Langfuse 的阶段追踪 |

前端复用统一日志入口，后端复用 Python logging 与统一上下文；业务代码就近补充关键事件。日志格式化、关联信息注入和脱敏由公共入口处理，避免各页面、各接口重复实现。日志代码不得反向依赖具体页面、改变业务结果或吞掉原异常。

Langfuse 承担模型和调用链观测，应用日志承担前后端业务事件与异常依据，两者用关联标识衔接。业务审计继续承担操作留痕，不用普通调试日志代替审计。

## 字段与关联

日志使用稳定的事件名及结构化字段，便于程序筛选；日志正文补充简短说明，不用全文搜索错误描述代替字段关联。

关联标识遵循最小充分原则：复用已有追踪和业务标识，不为日志另建一套 ID、数据库字段或映射表。下表是按场景选用的要求，不是每条日志必须带齐的字段清单。普通业务日志通常只需现有追踪标识，加一个有助定位的业务对象标识。

| 情况 | 字段要求 |
| --- | --- |
| 通用事件 | `timestamp`、`level`、`service`、`event`；时间包含时区，服务区分浏览器、Next.js、API 和 worker |
| 业务阶段 | `stage`、`status`；终结事件记录 `duration_ms`，区分开始、成功、失败、跳过、取消和等待重试 |
| 主关联 | 有有效 OpenTelemetry 上下文时复用 `trace_id`，不为同一次调用再生成第二个日志追踪 ID；`span_id` 由追踪系统管理，普通日志不强制重复记录 |
| 业务定位 | 使用当前处理对象的已有 ID，例如摄取用 `document_id`，单条问答用 `message_id`；只有定位确实依赖所属范围时，再补会话或知识库等标识。未知或无关字段不输出 |
| 后台任务 | 沿用业务对象 ID；排查重试或并发任务时，再记录 Celery 已生成的 `task_id`、重试次数，不另建日志任务 ID |
| 失败 | 稳定的 `error_code`（存在时）、`error_type`、脱敏原因；需要堆栈时按下节记录 |

同一调用已有的追踪上下文应在浏览器、Next.js 转发和后端之间传递，跨请求操作通过文档或消息等已有业务标识关联。未启用追踪时，先使用足以定位的业务标识；只有现有标识确实无法区分并发 HTTP 请求且需要跨端排查时，才补充 `request_id`，并由一个请求边界生成、其他层原样传递，不逐层重新生成。传递方式和响应约定按[接口规约](api-contract-conventions.md)维护，不在各业务中另定协议。

API 提交后台任务时传递追踪上下文或可回溯的追踪关联；任务和重试保留业务对象标识。异步操作可使用父子 span 或明确关联，不强迫整个长任务始终保持同一个活动 span。来自浏览器的 ID 是排查线索，不能代替身份校验或资源授权。

例如，一条文档转换失败日志通常记录 `trace_id`（可用时）、`document_id`、阶段、结果和脱敏原因即可；这不是要求同时记录请求、会话、消息、Bot、知识库及任务的全部标识。不要把不同请求或不同重试强行合并为同一次调用，也不要仅为使用日志增加接口字段或业务数据模型。

## 打点、级别与归因依据

- 在关键业务动作和阶段边界记录开始及终结事件，异常路径也要有终结结果。不要在每次组件渲染、输入变化、轮询响应、流式 Token 或内部循环中逐条打印。
- `INFO` 记录必要业务事件和结果；`WARNING` 记录可恢复异常或降级；`ERROR` 记录失败；`DEBUG` 用于按需诊断，生产默认关闭。用户主动取消、空检索结果或预期校验失败不能机械归为系统错误。
- 记录有助于判断的摘要，例如解析器、页数、图片数、分块数、检索数量、索引类型、模型、耗时和外部响应码；不打印完整正文、向量或原始请求响应。
- 异常在能解释失败阶段的边界记录一次完整且脱敏的堆栈和异常链；上层补充影响与关联标识，避免每层重复输出同一堆栈。包装异常保留底层原因，不只留下“请求失败”或“摄取失败”。
- 降级、回退、重试和最终失败分别记录；日志中“提交成功”不能等同于“后台完成”。日志级别也不能代替业务状态。
- 归因以实际失败事件、依赖响应和异常链为依据。区分已观察事实、推测原因及待补证据；不能仅凭最后一条错误或缺少日志断言根因。

## 浏览器日志、采集与脱敏

浏览器日志默认位于浏览器，Next.js 服务端日志位于服务器；`console` 输出不会自动进入后端或 Langfuse。开发时从浏览器控制台和网络面板定位前端事件；需要导出或集中查看时，使用受控的诊断导出/上报入口，明确可见范围与存放位置。

集中采集浏览器日志时，应校验允许字段和身份/访问范围，限制批量大小与频率，并处理去重、截断及保留期限；浏览器上报内容按不可信输入处理。生产只采集必要事件，详细调试按需启用。采集失败不改变业务结果，不递归上报自身错误；限流或丢弃应有可观察摘要。

普通日志、诊断导出和浏览器上报默认遵循以下脱敏要求；追踪中的业务内容沿用项目现有授权、配置和访问规则，不直接复制到普通日志：

- 不记录密钥、Authorization、Cookie、令牌、密码、完整企业文档、截图/base64、聊天正文或模型原始 Prompt/响应。
- 不直接序列化整个 Axios/HTTP 异常、请求配置、表单或响应对象；URL 查询串、异常消息与堆栈也需检查敏感值，只保留必要路径、状态和摘要。
- 原文和图片通过受权限保护的业务资源定位，日志只保留必要引用。原始诊断材料按[目录约定](project-layout.md)存入私有数据目录，不提交 Git。

日志输出和保存使用有界的缓冲、文件轮转或平台保留策略，避免无限增长；不得因上报、写日志或追踪导出阻塞主业务。

## 排查入口与验证

排查从现场实际可得的追踪或业务标识开始，例如 `trace_id`、`document_id` 或消息标识，不要求同时提供多种 ID。按关联关系取得有关前端、API、worker 事件及 Langfuse 追踪，输出时间范围、阶段结果、耗时、重试、最早可确认的失败依据，以及缺少的日志或追踪；未收集到的范围明确标出，不能报成“无异常”。具体查看方式维护在[开发环境说明](development-guide.md)。

新增或修改功能时覆盖实际涉及的关键阶段，不要求为了采用本规约先全仓补点。验收按影响验证：

1. 正常操作能关联前端请求、后端结果及必要后台任务，ID 不串到并发请求。
2. 前端异常、网络/超时或 WebSocket 失败能定位到具体动作；主动取消与失败区分。
3. 后台转换失败或索引失败能看到对应文档、阶段、底层原因和重试结果。
4. 模型或外部依赖失败能关联应用日志与追踪；追踪未启用或导出失败时，业务日志仍可用于排查。
5. 敏感内容不进入日志，采集故障不影响业务，重复异常和高频事件不会无限刷屏。

仅增加日志语句、写好规约或看到一次日志输出，不代表上述排查链路已经运行验收通过；实际实施和检查结果放在 `records/`。
